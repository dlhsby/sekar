- 2026-08-13 — **Worker pins wear their role's colour; the setting had been loaded and thrown away.** `buildRoleMarkerMap` selected `marker_icon` only, so `roles.marker_color` — configurable in role settings since ADR-044 — reached nothing: every worker pin drew white, whatever an operator set. The DTO now carries `role_marker_color` and it **fills the pin body**, while presence keeps the **ring**. That is deliberately the opposite call to the geo tiers made the same day, and for a reason that generalises: a geo pin sits on a boundary that already carries area identity, so its colour was redundant and became noise; a worker pin has nothing else to say WHO this is. Identity on the body, status on the ring — colour never means two things on one marker. Teams were already correct (team category `marker_color` + `marker_opacity` on the bubble). Mobile mirrors it: the pin body takes the role colour and presence keeps the arrow plus the luar-area ring, falling back to the presence colour when a role has none, so a role without a configured colour looks exactly as it did. **The colour was dropped twice, one layer apart:** after `buildRoleMarkerMap` was fixed, pins were still white because `computeSnapshot` rebuilds each worker field-by-field into `SnapshotWorker` and copied `role_marker_icon` without its new sibling — a hand-written projection silently omits a field that a spread would have carried, and the types can't catch it while the target interface is missing the field too. Both now carry `role_marker_color`. be 406 monitoring · mobile 4475 · web 2288 green.

- 2026-08-13 — **Four field-test findings: emulator teleport blocked the punch, the map fitted to an outlier, the trail drew itself, and geo pins wore the wrong colour.** (1) **`Gagal clock out` on an emulator.** The integrity override skipped only the MOCKED rule, on the reasoning that impossible travel is a geometric fact independent of the provider — true, and beside the point: **a mock provider is one you move by typing coordinates**, so a tester who checks Jakarta and then Surabaya has "travelled" 700 km in a minute, and the rule blocked the punch itself. Anything already trusting a self-declared mocked fix has no stricter claim to make about the distance between two of them. `IMPOSSIBLE_TRAVEL` now relaxes with the same dev-only, non-production gate; **null island stays rejected** — (0,0) is a broken fix rather than a movement, and nobody tests there. Production is unchanged and has its own regression test. (2) **The initial fit included worker positions**, so one satgas standing in Jakarta opened the map on the whole of Java with Surabaya an unreadable smudge. The served region is a property of the DATA — which rayon and lokasi the role can see — not of where somebody happens to be standing, and an out-of-area worker is precisely when the city most needs to stay legible. Fit is geography-only; the worker is still reachable via search or the Petugas list, which pan to them. (3) **The trail was a side effect of selection.** Opening a worker from search drew a line from wherever their day started, across the map when that was another city, on top of a card meant to answer "where are they now". It is now opt-in behind **Lihat jejak** (toggling off on a second press, cleared when the selection moves to someone else), which also stops a location-history request firing for every worker merely glanced at — and it gained **start / end markers**, matching mobile: a bare line says where someone went but not which way. (4) **Geo pins are white.** They took each area's `fill_color`, putting the map's loudest colour on its most repeated element, so at zoom the pins competed with the polygons wearing the same colours and a rayon's identity read twice. Boundaries now carry area identity; colour on a geo pin means STATUS (the health badge) alone. **People keep their colours** — role marker and team category — because those are the markers where colour still identifies something. Mobile needed no change here: its node bubbles were already white with a health-coloured border. be 2823+ · web 2285 green, i18n parity ✓.

- 2026-08-13 — **Viewport mode gained depth (a bbox alone wasn't enough), and any row can be hidden.** Tested on real data, viewport mode still drew every kawasan and lokasi at the city view — obviously, in hindsight: **at city zoom the box IS the city**, so "only what's on screen" narrowed nothing. The fix is the other half of what any detail-carrying map does: **tiers arrive as there is room for them.** Rayon near the city; kawasan once the camera is at roughly one rayon (zoom ≥ 13 / `latitudeDelta` ≤ 0.05); lokasi and the workers in them closer still (≥ 14.5 / ≤ 0.015 — the same threshold `UserMarker` already used to decide a label is readable, so a pin never appears without a name it can carry). Below the kawasan threshold the client asks for `level='district'`, so lokasi geometry is not merely undrawn, it is **never downloaded**. A missing tier must read as "not yet" rather than as broken data, so the map carries a **"Perbesar untuk melihat kawasan / lokasi"** hint until it is at full depth. Zoom mode is untouched — everything at every zoom is the trade chosen there. **Row-level hide** lands in both side-panel tabs: 371 Wilayah rows is not a list, and hiding by tier is too blunt when the thing in the way is one rayon. Persisted per browser (`monitoring.hidden.v1`) beside the layer facets, because it is a workspace preference and not a data change, under three rules — **hiding is presentation, never accounting** (counts come from the server over the full scope, so a hidden lokasi is still counted inside its rayon and the tab badges still report what is in scope); **never silent** (a hidden-count banner with one-click restore, shown even when *everything* is hidden, where an unexplained empty state would be the only other feedback); and **a hidden node hides itself, not its subtree**. Hidden rows leave the map too — not seeing the pin is the point. The worker row had to split into two targets (a button nested in a button is invalid HTML), which also caught a page test matching the hide button's label by accident. Mobile gets the depth gate on the same thresholds; row-level hide there is still open. mobile 4466 · web 2283 green, i18n parity ✓.

- 2026-08-13 — **A third map mode that only loads what is on screen, and the mode control became a select.** Shown the real map, the client accepted zoom mode's cost and then asked the better question: same everything-at-once view, but only for what she is actually looking at. **`viewport`** draws exactly what zoom draws — one `isZoomLike(mode)` helper backs every rendering decision, so the two cannot drift into showing different things — and differs only in what it asks for. The bounds go to the **server**: `GET /monitoring/boundaries?bbox=` returns only geometry intersecting the box, and `?scope=all&bbox=` **skips the builder passes** for off-camera districts rather than discarding their results. Culling alone could never have done this; the client was already culling, and still paying for ~1.5 MB of city-wide geometry. Three decisions keep it honest: bbox tests are **bounding-box, not true intersection**, and err toward *including* a shape — over-inclusion costs a few KB, under-inclusion blanks a boundary the operator is standing inside; **geometry beats centre**, because a rayon big enough to fill the screen has its centre off-camera; and **totals never move** — `totals`/`roster_totals` stay scope-wide and a rayon's `area_count` stays its true size, since a number that shrank while panning reads as data vanishing rather than as a viewport. Client-side the box is **padded by half a screen** and redrawn only once the camera leaves it, so ordinary panning is free, and it is part of the query key so panning back is cache-served. A malformed `bbox` is ignored rather than rejected — a bad value degrades to the full payload instead of blanking the map. The mode control is now a **select** (three options no longer fit as tabs without truncating their labels), and an unrecognised stored mode falls back to drill. Mobile gets the same third mode, where it matters more: mobile asked for `level='area'` **city-wide in every mode**, i.e. every lokasi polygon in Surabaya, on the connection least able to afford it. be 2823 · mobile 4458 · web 2257 green, i18n parity ✓.

- 2026-08-13 — **Label split from marker, and each tier's name moved to its own side.** Two asks, one root cause: every name printed directly under its pin, clipped to a single line. A lokasi inside a kawasan inside a rayon therefore wrote three names on the same strip of map, and none of the three was readable. Names now go **rayon below · kawasan left (right-aligned) · lokasi right (left-aligned) · petugas and tim above (centred)**, so overlapping tiers write in different directions, and they **wrap** instead of running off across the map. The mapping lives in one constant per platform (`NODE_LABEL_PLACEMENT`) because web draws node labels from two call sites — the node layer and the drilled-in current-node pin — and a name that changed sides on drill-in would read as a bug. **`label` is now its own facet** beside `marker`: a dense tier is routinely wanted as pins alone (at city zoom every lokasi name at once is unreadable while the pins still carry the counts), which the combined control could not express. Migrations map v5 `'marker'` → `['marker','label']` since that option drew the name too. The two platforms diverge in mechanism, not result: web positions the label absolutely outside the pin box (`.am-label--top/bottom/left/right`, `overflow-wrap: anywhere`, `max-width: 132px`) so the anchor never moves; **mobile cannot** — `react-native-maps` anchors by a fraction of the rendered view and Android snapshots that view to a bitmap, clipping anything outside its bounds, so a label positioned outside the pin would simply vanish. Mobile instead reserves an **equal empty slot on the opposite side** (`LabeledMarker`), keeping the pin at the view's exact centre so `anchor` stays `{0.5, 0.5}` and the pin does not drift as the name lengthens; the slots are fixed-size for the same reason, so names wrap to at most two lines. Mobile's node and team names also moved OUT of their bubbles, where they had been clipped at 160/170 px. `UserMarker`'s name moved above its pin, which incidentally fixes its anchor: with `anchor.y = 1` the bottom of the view was the label's bottom edge, so the arrow tip never sat on the coordinate — now it does. mobile 4451 · web 2243 green, i18n parity ✓.

- 2026-08-13 — **Layer rows became multi-select facets, and "fill" is finally its own control.** The client's read of the four-way select was "it's confusing to select which one" — the widget made you translate what you wanted into one of four named states, and the naming hid the real problem: **`Batas saja` silently meant outline AND fill.** A polygon's wash is the heaviest thing the map paints and it had never been separately expressible, in any generation of this control. Each geo row is now three INDEPENDENT checkboxes — **Batas / Isian / Marker** — and personnel is **Petugas / Tim**; `Semua` and `Sembunyikan` survive as shortcuts that write the same set the boxes do, so a "select all" affordance can never disagree with the boxes under it. Storage `monitoring.layers.v6`, migrating **both** older keys directly (v4 booleans and the v5 enum) rather than chaining through v5's own lossy step; v5 `'boundary'` maps to `['boundary','fill']` so nobody's map loses a fill it currently has, exactly as v4 `false` maps to `['marker']` so nobody loses pins. Rendering splits accordingly: the polygon is mounted on `showsPolygon` (**either** facet — gating on the outline alone would drop a fill-only tier entirely), then the facets set `strokeOpacity`/`strokeWeight` and `fillOpacity` independently. Mobile mirrors it: the tap-to-cycle row is gone (cycling cost up to three taps for a two-facet change and hid the options you were not on) in favour of the same chips, and `react-native-maps` has no `fillOpacity` prop — the alpha lives in the colour — so "fill off" is a transparent fill, not an omitted polygon. **`tim` without `petugas` is now legal** and means teams-only, the reading the v5 single-select was built to forbid; the combination that drew an empty map is instead simply the empty set, which is what "hidden" should always have meant. Row labels dropped their "Batas " prefix (Rayon / Kawasan / Lokasi) — a row that governs three facets is not a boundary row. Two stale fixtures fell out: `MapDashboardScreen`'s mocked store still carried the pre-v5 keys (`workers`/`districts`/`areas`) and only passed because comparing a missing key against a string quietly said no. mobile 4448 · web 2239 green, i18n parity ✓.

- 2026-08-12 — **Daftar Petugas aligned to both modes, and search can finally find a kawasan or a lokasi.** Reviewing item 5 turned up a real defect rather than a gap: `useMonitoringSearch` read the map's **scope-bound** boundaries query, and at CITY scope — the default view — the page asks `level='district'`, so `.areas[]` and `.regions[]` come back empty and **no lokasi was findable from the screen a supervisor searches from most**. Kawasan was worse: the hook had no `region` result type at all, so it was unfindable at every scope. New `useGeoIndex()` asks for the full hierarchy once (`level='area'`, no district id — the identical call zoom mode already makes, so they share a cache entry), keeps only id/name/tier/centre/parent and drops the geometry, which is much the larger half of that payload. Search gained the `region` type; results are ordered petugas → lokasi → kawasan → rayon (narrowest geography first, since a lokasi name is more specific than the rayon containing it); picking a kawasan now drills to it. Entries with no centre are dropped — a result you cannot fly to is not a result. A rayon has no parent to show, so it keeps reporting its size as the subtitle, exactly as before. **Sidebar:** the Wilayah tab now lists what the map draws — in zoom mode the whole subtree, ordered rayon → its kawasan → its lokasi with tier chips and indentation, region-less lokasi sitting directly under their rayon, and the node you are standing on omitted because the breadcrumb already names it. Node rows gained the **presence** numbers next to the roster trio (Aktif / Tidak Aktif / and Luar area only when non-zero): the roster says who was *expected*, presence says who is *reachable now*, and a row carrying only the roster cannot answer the question the map exists for. The Petugas tab count was already bound to the map's own predicate in the zoom-mode change, so the tab and the map cannot disagree in either mode. web 2216 green.

- 2026-08-12 — **Zoom mode: a second map mode that shows every tier and everyone in it ([ADR-060](../../architecture/decisions/ADR-060-monitoring-map-modes.md)).** Client wanted the city view to show all rayon/kawasan/lokasi and all workers at once, with a rayon tap narrowing to that rayon's *whole subtree* instead of its immediate children. She was told it would be heavier and insisted, so both modes ship and `drill` stays the default (`monitoring.mode.v1`, localStorage, beside the layer selects). The modes ask genuinely different questions — drill: *is this worker's schedule scoped here* (`scopeMatches`, ADR-046 `display_scope`); zoom: *is this worker standing anywhere inside this* (`subtreeMatches`, real geography) — so they are named and selected in one place rather than blended. A consequence: in zoom mode an **ad-hoc clock-in shows inside the rayon they are physically in** despite their flat city `display_scope`, still styled Luar Jadwal (visible, not counted). Zoom needed no new endpoints: it reads the **city snapshot at every level** (already every live worker, with full parentage) and asks `boundaries?level=area` without a district id (already every tier's polygons), plus one `aggregate?scope=all` in place of the 1 + 2N drill calls. **The modes differ only in what is drawn — no count is re-derived**, which makes a cross-mode discrepancy a detectable bug rather than an expected difference. Perf is **viewport culling only, never clustering**: clustering was removed from this map on request ("it hid people and confused operators") and bringing it back inside the mode built to show everything would be self-defeating, so culling merely defers off-screen overlays and panning restores them. Boundaries are culled too — in zoom mode the polygons cost more than the pins. Honest limitation: a fully zoomed-out city view culls nothing and stays the worst case by construction; that is the client's explicit trade, to be measured and reported rather than silently capped. The lokasi outlines still follow the RAW node-marker set, not the layer-filtered one, so hiding markers never takes the boundaries with them. web 2206 green.

- 2026-08-12 — **Layer toggles became selects, and node markers can finally be hidden.** Client asked for the "Lapisan Peta" switches to become options (`Semua` / `Batas saja` / `Marker saja` / `Sembunyikan`) applied to every tier. That surfaced a real gap: a v4 toggle governed the **boundary only** — node markers were drawn unconditionally and there was no way to ask for "markers, no outline" (or to hide them at all). It was deliberate at the time, so a supervisor could never hide the map's primary content; the client overrode it, and drilling still works from the Wilayah sidebar when markers are off. `MonitoringLayers` is now four selects: `district`/`kawasan`/`lokasi` (`LayerVisibility`) + `personnel` (`PersonnelVisibility`). Petugas/Tim collapse into **one** select because they were independent booleans that could express a state meaning nothing (Tim on, Petugas off → empty map), previously papered over with a disabled-state hint — one select makes it unrepresentable rather than discouraged. `tim` means *only team members, collapsed*; `petugas` means everyone as individuals. The map asks predicates (`showsBoundary` / `showsNodeMarker` / `showsWorkerPins` / `showsTeamBubbles` / `teamMembersOnly`) instead of comparing strings, and node markers filter on their existing `variant`, so `NodeMarkerLayer` stays unaware of layer settings. Storage moved `monitoring.layers.v4` → `v5` with a migration whose subtle half is `false`: a v4 "off" maps to **`'marker'`, not `'none'`**, because the old toggle never hid the pin — mapping it to `none` would silently remove markers that were on screen before the upgrade. **No `city` row**: rayon/kawasan/lokasi each own a `boundary_polygon`, Surabaya is not an entity in the geography model, so a city row would be a control with nothing to draw — flagged to the client. web 2197 green.
- 2026-08-12 — **Backend for the map's zoom mode: `aggregate?scope=all`, and a search that can find someone who hasn't clocked in.** Client feedback asked for a second monitoring mode showing every rayon/kawasan/lokasi and every worker at once. Two things turned out already to exist and be unused: the **city snapshot already returns every live worker** (`computeSnapshot('city')` passes an empty filter) carrying `display_scope` *and* `district_id`/`region_id`/`location_id`, and **`getBoundaries({level:'area'})` with no `district_id` already returns every district + region + area polygon** — the web simply pins `level` to `'district'` at city scope. So zoom mode needs no new worker or geometry endpoint. The one real gap was node COUNTS: `/monitoring/aggregate` took `city|district|region` and both child builders require a `districtId`, making all-tiers-at-once 1 + 2N requests. Added **`scope=all`**, which loops the active districts and calls `buildDistrictNodes`/`buildRegionNodes`/`buildLocationNodes` **verbatim**, each district's children built with that district's *own* `clockedInUserSet` exactly as `scope=district`/`scope=region` do. Deliberately not optimized into one wider grouped query: a node's counts must be *provably* identical whichever mode asked for them, and this is the code that shipped the tier-guard bug twice — reuse makes that identity a property of the code rather than a claim. `totals`/`roster_totals`/`presence_totals` come from the **district tier only** (Σ all tiers would count each worker in their rayon, their kawasan *and* their lokasi). Nodes already carry `type` + parent ids, so no DTO shape change. Scope enforcement mirrors the drill scopes — a rayon-scoped role is pinned to its own subtree, so zoom mode is not a way around it. **Search** now also matches workers **rostered today but not clocked in**: the live query is rooted in `user_tracking_status`, so it structurally cannot surface them, and typing a known satgas's name returned nothing whenever they hadn't punched in. The narrowing applies to `absent_users`/`on_leave_users` **after** both lists are built, not to the rows before — `absent_count` is derived from the list, so filtering upstream silently redefined the count into a match count (caught by the spec asserting counts stay put). Specs cover composition rather than SQL: node set = concatenation of the drill calls, per-district clocked-in sets, id narrowing, and totals taken from the district tier. be 2804 green.

- 2026-08-07 — **The liveness guard reached only the city tier; rayon / kawasan / lokasi still counted phantoms.** The previous entry fixed `getLiveUsers` and the roster summary, but **twelve** other `user_tracking_status` reads still said `uts.shift_id IS NOT NULL` with nothing checking the session was open — and they are exactly the drill tiers: `buildDistrictNodes` (rayon), `buildRegionNodes` (kawasan), `buildLocationNodes` + `getAreaWorkers` (lokasi), plus `countableOnlineByGroup`, `presenceByGroup` and the three `count*ByAreaIds` roll-ups. Drilling into any tier therefore still showed staffing measured against sessions that ended days earlier. Worst of them was `clockedInUserSet`, which feeds `offScheduleCount`: a phantom is by definition absent from today's roster, so **every stale row was counted into the "Luar jadwal" pill** — the origin of *Aktif 0 · Luar jadwal 259* on a city view with nobody on duty. All fourteen now share one `LIVE_SESSION_SQL` predicate (EXISTS against `shifts`, not a join — the tier queries already join `area`/`user` and group by them). It tests a **fact** (the session is closed) rather than re-deriving ADR-055's window rule in SQL; that rule stays in `endStaleSessions`. Two sites keep the `FindOptions` spelling via the `shift: { clock_out_time: IsNull() }` relation condition, deliberately: converting them to query builders shifted the strictly-ordered `mockReturnValueOnce` chains in the aggregate specs, which is churn for no behavioural gain. **Verified against the staging clone with a planted phantom** (a tracking row pointing at a shift closed 3 days earlier): invisible at city, rayon and lokasi, while a genuine live worker still appears at all three — and the SQL differential is explicit, old predicate counts it, new predicate does not. **Display was already correct on both clients** and is unchanged: `display_scope` puts a scheduled worker only at their own tier, an ad-hoc clock-in is pinned to **city** with `is_scheduled: false` + the `ad_hoc` flag ("Luar Jadwal" marker), and `apps/mobile/src/utils/monitoringScope.ts` mirrors the web `scopeMatches` canon exactly. Confirmed live: a scheduled worker returns `display_scope=location`, an unscheduled one `display_scope=city, ad_hoc`.
