# Auth — Changelog

Newest first. Feature overview + current design live in [README.md](./README.md).

- 2026-08-21 — **Only a refusal ends a session; a broken server does not.** The expiry work shipped the day before split refresh failures into `rejected` vs `unavailable` on the test "did the server answer?" — which is right for a timeout or aeroplane mode, and wrong on **deploy**. Behind nginx or an ALB a rolling restart does not connection-refuse, it answers **502/503**, and that IS a response: any worker whose access token happened to expire inside the deploy window would have had the 502 read as "your refresh token is bad" and been signed out mid-shift. Only **401/403** now count as a refusal; every other outcome — no response at all, 5xx, 429 — is `unavailable`, which keeps the credentials and reports a network error so the caller queues the work offline. The distinction is between the server saying *this credential is bad* and the server saying *I am broken right now*, and only the first is about the session. **Four existing specs turned out to be passing for the wrong reason:** they mocked the refresh endpoint as the bare path `/api/v1/auth/refresh`, which never matched the absolute URL `refreshAccessToken` posts to, so "refresh returns 200 with no token" and "refresh succeeds then 401s again" were both silently exercising the *unmatched request* branch instead. Pointed at the real URL, they now test what their names claim — and every `MockAdapter(axios)` in those files is now built with **`onNoMatch: 'throwException'`**, so a mock that matches nothing fails loudly instead of quietly routing the test through the unmatched branch. That guard is the actual fix: hunting instances finds the ones you know about, while the flag makes the whole class impossible. Verified by re-introducing a bare-path mock and confirming the suite fails. Also written down as a deploy invariant in `specs/deployment/README.md`: **`JWT_SECRET` must not be rotated as a side effect of a release** — every token is signed with it, so changing it signs out the entire fleet at once, and pointing an environment at a different or renumbered database does the same thing (ordinary migrations do not, since user ids survive them). mobile 4498 green, tsc + lint clean.

- 2026-08-20 — **A dead session now actually signs the worker out, and their unsent work survives it.** The 401 path called `clearAll()` and stopped there: the tokens were gone while Redux still held `isAuthenticated: true`, and `RootNavigator` gates on `isAuthenticated && user`, so the worker stayed INSIDE the app on a session that could no longer talk to the server. Every request 401'd, the tracker kept pumping pings into the offline queue, and the only symptom was a toast reading "Sesi tidak valid. Silakan masuk kembali." with no way to act on it. Four changes, under the constraint that **no data may be lost**. (1) **`apiClient` cannot dispatch.** The store's thunks import `apiClient`, so importing the store back closes a require cycle — and Metro resolves a cycle to `undefined` at module-init rather than throwing, so the mistake would not crash, it would silently hand you a `dispatch` that is not a function at the exact moment the app must react. New `services/auth/sessionEvents` inverts it: the transport announces, a root-level subscriber decides. It **latches**, because when a token dies every in-flight request fails together and each one would otherwise drive its own logout, its own navigation reset and its own toast. (2) **A rejected refresh token and an unreachable server are no longer the same event.** `refreshAccessToken` returned `null` for both, so a field worker in a basement or under canopy would be signed out by a bad signal; it now returns `refreshed | rejected | unavailable`, keyed on whether the server ANSWERED, and `unavailable` keeps the credentials and reports a network error so the caller queues offline exactly as before. (3) **`useSessionExpiry` performs the teardown** — stop the tracker first (it is the only thing still producing work), disconnect the websocket, reset the auth/shift/activities/notifications slices, then `logout()` last so navigation only unwinds once the state behind it is consistent. It deliberately does **not** call `clearQueueForCurrentUser` / `clearOrphanedItems` the way the voluntary path does: voluntary logout offers to sync first, this one arrives unannounced and mid-shift. The offline slice is not reset either — it mirrors the surviving queue, and zeroing the pending count would tell the worker their unsent work is gone. (4) **The queue's own data-loss path.** `addToQueue` stamps `user_id` from `getUser()`, which reads the EncryptedStorage `clearAll()` had just wiped, so pings queued in the gap were written ownerless — and `clearOrphanedItems` deleted exactly those at the next voluntary logout, silently and hours later. Being unattributed is survivable on its own, because `syncManager.processQueue` reads `getQueuedItems()` — every item regardless of owner — so the ping still syncs; being **deleted first** was not. The sweep now removes only items EXPLICITLY marked `orphaned`: "no owner recorded" is not the same claim as "belongs to nobody", and a pending item is unsent work. (An earlier attempt also re-attributed such pings from a remembered last-owner key; it was dropped once `getQueuedItems` proved attribution unnecessary for the guarantee, and it added module state plus a write on every queue read.) The tracker also stops treating 401 as transient — it holds its persisted buffer for the next session instead of queueing pings against a session that is already being torn down. mobile 4497 · be 2826 green, i18n parity ✓.
