# Attendance — Changelog

Newest first. Feature overview + current design live in [README.md](./README.md).

- 2026-08-01 — **Clock-in/out selfies stop landing in Postgres as base64 (500 MB across three columns).** `PhotoUrlInterceptor` has converted inline media globally since the F9 tier-2 Phase A work, but it only rewrites the photo **field names** in its map — and a selfie arrives as **`selfie_photo`**, which was never in it. So every clock-in and clock-out photo went straight into `attendance_punches.photo_url` and the projected `shifts.clock_*_photo_url` as a raw data URI. On the 2026-08-01 staging clone that was **1,361 punches / 250 MB + 773 clock-ins / 140 MB + 588 clock-outs / 110 MB — 100% of rows, averaging 188 KB, largest 634 KB**, and `shifts` (269 MB) + `attendance_punches` (267 MB) were the two biggest tables in the database. (1) `ShiftsService.storeSelfie()` now puts the photo in object storage and the column holds a URL; overtime inherits it, since `startOvertime`/`endOvertime` delegate to `clockIn`/`clockOut`. (2) An already-stored URL passes through untouched, and the four selfie DTOs' `@Matches` — which **required** a data URI — now accept either, so a client that starts uploading separately needs no API change. (3) `attendance_punches.photo_url` was missing from the `backfill:inline-photos` target list entirely (the script predates ADR-055's punch table), and is now first in it, with content-hash dedupe so the 776 byte-identical punch/shift pairs upload once. Backfill re-run on the clone: **2,905 photos / 398.9 MB in 1 m 55 s, zero failures**, all columns 0 inline, DB **658 MB → 100 MB** after `VACUUM (FULL)`. Photos still render — stored URLs presign on read and fetch 200 `image/jpeg`. (4) **Two more holes in the same interceptor, found while verifying every consumer.** Its FIELDS map is keyed on the JSON property — the ENTITY PROPERTY, not the column — and three entities name them in camelCase (`Activity.photoBeforeUrl`/`photoAfterUrl`, `PruningRequest.photoUrls`, `NotablePlant.photoUrls`), so those were skipped in BOTH directions: base64 persisted on write, URLs sent **unsigned** on read. Unsigned means broken, not merely unsigned — the bucket is private and a raw object URL answers **403** (verified). Both spellings are now mapped. (5) **Presigned links expire (24 h) and mobile cached one across boots.** `AuthProvider.restoreSession` already fetched `/auth/me` on startup but merged only `location_id`/`district_id`, so the avatar stayed the link signed at *login* and 403'd a day later, recovering only if the worker opened Profil. It now takes the fresh one from the response it already had. End-to-end proof: a multipart upload lands a bare URL in the column (no base64, no signature), the API returns it presigned, and the browser decodes it — 2 images loaded, 0 broken, 0 storage errors. be 2671 · mobile 4390.
- 2026-07-31 — **`active_shifts` counted every never-closed session ever recorded.** `GET /monitoring/city` (and the per-district count) reported **528 active shifts against 3 genuinely open** on the staging snapshot: both queries were an unbounded `clock_out_time IS NULL`, so 525 historical forgotten clock-outs were still being reported as workers on duty. ADR-055 is explicit that a dangling session past its cutoff is **not** live (`pulang` + `lupa_clock_out`) — the roster presence layer honoured that, `monitoring-stats.service.ts` did not. Both counts are now bounded to **today's service day** (WIB). Known limit, stated rather than hidden: a *same-day* dangling session still counts toward this raw number; the authoritative counting axis remains the ADR-050 presence layer, not this tile. Same pass: the record page's out-of-area banner is **removed** (the pre-punch confirm already names it — one statement, not two), and **Detail Shift** is now the same ghost button as Jadwal / Log Kehadiran instead of a bespoke uppercase mono link.
- 2026-07-31 — **One Kehadiran card everywhere; the picked shift is the shift you are graded against.** (1) The home hero's bespoke "SEDANG BERTUGAS" card is **gone** — on duty now renders the SAME `AttendanceEntryCard` as the idle state and the hub, with a new `infoRows` slot carrying Status Kehadiran / Status Area. Removed with it: the expand/collapse that hid Clock Out behind a tap, the duplicate "Jadwal saya" block (the card's Jadwal button covers it) and the Detail Shift link (reachable from Log Kehadiran — one entry point, not three). (2) **Shift selection moved into `useClockInOut`.** It was screen state, so `resolveActiveShift` still graded against the server's *default* option: picking Shift 3 at 20:37 showed "Shift 3" and **TERLAMBAT**, because lateness was judged against Shift 2. The hook now owns `selectedShift` (seeded caller-preference → default → first, keeping an explicit pick across refetches, keyed `service_day:shift_definition_id`), and label, status and `isLate` all read it. (3) Area Tugas states the **distance to the assigned area** ("1,9 km dari Rayon Barat 1") — "Di luar area" alone never said whether that was 20 m or 700 km. (4) Fixed a **time-dependent test** that passed in the afternoon and hung at 21:00: its Shift 3 fixture became late, raising a confirm nothing pressed.
- 2026-07-31 — **Multi-shift day showed the wrong shift, and graded against a third one (mobile).** A worker rostered to Shift 2 (15:00–23:00) *and* Shift 3 (21:00–05:00) read as "Shift 3 · TEPAT WAKTU" at 19:00 — four hours late for Shift 2 and told they were on time. Backend was correct throughout (`/shifts/current-state` returned exactly one candidate, Shift 2 `covering`; Shift 3's 60-min early window opens at 20:00). The client was the problem, in two places: the label came from attribution while **lateness was derived from `/schedules/my`'s single row**, which on a multi-shift day can be the not-yet-started shift — so the surface could name one shift and judge another. New pure `resolveActiveShift(options, rosterShifts, now)` + `pickOperativeShift(shifts, now)` (`utils/shiftDisplay.ts`, crosses-midnight aware) return **one full `ShiftDefinition`** — attribution-first, falling back to the roster row *covering now* rather than an arbitrary one — and label, status and `isLate` all read it on the record page, home hero and hub. `pickDisplayShift` alone was insufficient because it returns no `crosses_midnight`, which lateness needs.
- 2026-07-31 — **Pre-punch confirmation (mobile).** A punch that will be recorded unfavourably now says so *before* it is submitted, instead of only after. New pure `buildPunchWarnings()` (`utils/punchWarnings.ts`, unit-tested incl. the crosses-midnight wrap) raises **one** dialog listing **every** applicable reason — `outside_area` (with the area name) · `late` (duration + shift start) · `outside_window` (shift already ended) · `early_leave` (duration still owed, projected against *now*, since `isEarlyLeave` reads a clock-out that hasn't happened) · `no_schedule` (ad-hoc, **not counted in monitoring**) — closing with "Kehadiran tetap dicatat". Advisory only: **there is no approval step** (cf. the dropped Koreksi Kehadiran), so cancelling merely abandons the punch and nothing gates on GPS — the confirm button is therefore plain "Clock In"/"Clock Out", not "Tetap …". Same pass tightened three unscheduled-worker inconsistencies: the **"Anda belum clockin pada shift ini" banner no longer fires when there is no roster row** (nothing was missed — new `hasScheduleToday` prop on `AttendanceEntryCard`, defaulting true); the no-shift label is now the single key `attendance:hub.noShift` ("Tidak Ada Shift") on home, hub **and** the Rekam Kehadiran card, replacing the page-local "Belum ada jadwal hari ini" (key deleted, not left to drift); and the **Ubah Shift pencil now appears only from two candidates up** (`shiftOptions.length > 1`) — a single candidate promised a choice that did not exist. Rekam Kehadiran's day/shift line is now the **shared `AttendanceShiftHeading`** (extracted from `AttendanceEntryCard`, so home/hub/record render one component) sitting **above Jenis Kehadiran**, replacing the "Jadwal Shift │ value" table row that stated the same fact in a different shape; the duplicated **Jam Masuk / Jam Keluar row is gone from the record page** (the entry card owns it — elapsed time stays in Detail Shift). Also adds `todayLocalDate()` to `dateUtils`, replacing a third hand-rolled local-day helper. `scope`/`none` area states stay silent — both are already stated inline and neither means the worker is somewhere they shouldn't be. Clock-out keeps its plain "are you sure" when nothing is off. Also fixes a latent guard: `!location.latitude` treated **latitude 0 as "no GPS fix"**.
- 2026-07-27 — **Roster reads now carry the presence axes (ADR-050).** Attendance state was only fully readable through `monitoring`; a roster read exposed `status` alone, so the Jadwal board could not distinguish "on duty outside the area" from "on duty", nor terlambat from present. `RosterPresenceService` now attaches `lifecycle_state`/`lifecycle_flags`/`leave_reason`/`is_within_area`/`is_scheduled` to `/schedules/range`, `/date/:date` and `/my/day`, derived by the SAME `derivePresenceState` monitoring uses. Flags land where they matter: `lupa_clock_out` vs `lembur` (never auto-inferred overtime), `is_late`, `excused` on sakit/izin so an approved absence never reads as a no-show. Also documents the **two coexisting time conventions** (`isShiftWindowClosed`/attribution take WIB-in-UTC-fields; `derivePresenceState`/`resolveShiftWindow` take real instants) after mixing them shifted the clock 14h. Full walkthrough + scenario matrix: [scheduling/PROCESS.md](../scheduling/PROCESS.md).
- 2026-07-27 — **Next-shift visibility (multi-shift day).** A worker with back-to-back shifts now sees what's next without opening Jadwal Saya. - 2026-07-27 — **Clock-in now advances the roster row to `present` (ADR-056).** As part of the schedule status lifecycle, `ShiftsService.clockIn` marks the day's `(user, service_day, shift)` roster row `planned → present` synchronously (non-overtime; wrapped so a status write can never fail the punch). - 2026-07-27 — **Mobile: city-scope (Penugasan Kota) clock-in now geofences against every rayon.** A worker assigned city-wide (roster row names no lokasi/kawasan/rayon → `resolveScheduleScope` = `city`) had no boundary polygon, so clock-in + the home hero showed the neutral **"Batas belum ditentukan"** — misleading, since it isn't a config gap. - 2026-07-25 — **ADR-055 adversarial-review fixes (multi-open sessions + explicit shift).** A 4-agent review of the whole punch surface surfaced three real defects, all from Phase-1 removing the single-open-shift guard (a worker can now hold a regular AND an overtime session at once): (1) **`clockOut` wasn't overtime-aware** — `findOne(clock_out_time IS NULL)` with no `is_overtime` filter could close the *wrong* session, so ending overtime might close the regular shift. `clockOut` gained an `isOvertime` param (default false); `overtime.endOvertime` passes `true`. (3) **`activities.getActiveShiftOrFail`** now deterministically attaches to the regular session first (`is_overtime ASC, clock_in_time DESC`). Tests added for each; 819 backend tests green.
