- 2026-08-02 — **Evidence photos are camera-only ([ADR-059](../../architecture/decisions/ADR-059-location-integrity.md)).** A gallery image is no evidence the worker was anywhere, which is the point of requiring a photo. Activity, task-completion and pruning photos now force a live camera capture; profile pictures are unaffected (not evidence). Gated twice on purpose: `mediaService.pickFromGallery` refuses outright — the real control, since a screen that forgets to hide its button must still be unable to attach one — and `isGalleryAllowed()` lets the UI hide the option so nobody taps a button that then refuses. Behind `ALLOW_GALLERY_UPLOAD`, `__DEV__`-gated so the emulator keeps the gallery and a release bundle cannot.
- 2026-07-21 — **Scope-aware tasks & activities — web + mobile UI.** Task create (web page + `TaskFormModal`; mobile `TaskCreateScreen` via `ScopeSection`) gains a **"Cakupan area"** selector: **Auto (ikuti jadwal)** [default] sends no `scope`/ids so the backend derives scope from the assignee's schedule; explicit **Kota / Rayon / Kawasan / Lokasi / Tanpa area** send `scope` + the matching id (district/region/location required, client-validated + localized). **Submit-activity-from-task (mobile):** `CreateActivityRequest`/`ActivitySubmission` route gain a `task_id`/`taskId`; `TaskDetailScreen` has a **"Submit Aktivitas"** entry for the assignee on an active task, so the activity inherits the task's scope. Monitoring needs no frontend change — a started task extending `display_scope` is server-computed and already rendered by the existing snapshot matching. Web PR #358, mobile PR #359. i18n id/en + web/mobile parity green.
- 2026-07-21 — **Scope-aware tasks & activities (ADR-046, backend).** Tasks and activities now carry a geographic **`scope`** (`city|district|region|location|none`, the shared `AssignmentScope` enum) that **follows the schedule assigned**, mirroring the monitoring drill tiers. **Task** gains `scope` + `region_id` (already had `location_id`/`district_id`): scope is **hybrid** — the creator may override it (`scope` + the matching id, validated) else it is **derived from the assignee's schedule occurrence** on the task date, else `none`. **Activity** gains `scope` + `district_id` + `region_id` + a `task_id` on the create DTO: an activity submitted **against a task** inherits that task's scope; otherwise it derives from the **active shift's** schedule occurrence; an unscheduled worker falls back to the shift's `location_id` (or `none`). **No-schedule workers are never blocked** — assignment, taking, and submission all succeed with `scope=none`. A **started (in-progress) task extends where its assignee renders on the monitoring map** (`display_scope`, deepest-wins). New `ScheduleScopeResolverService` (lean `ScheduleScopeModule`) is the write-side sibling of monitoring's `scheduleScopesForCurrentShift`. Dev uses TypeORM auto-sync; a prod migration for the new columns is a follow-up. Web/mobile form + display follow-ups tracked.
